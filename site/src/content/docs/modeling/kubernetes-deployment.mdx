A Kubernetes deployment view can answer:

- Which clusters and namespaces run each logical system or container?
- Which Deployment, StatefulSet, DaemonSet or CronJob represents it in each cluster?
- Which images and Kubernetes image IDs were desired and observed at the last successful refresh?
- How many replicas are desired, ready, available and updated?
- Which selected workload controllers are not mapped into the architecture model?

Answer stable questions in authored LikeC4. Refresh observed answers from Kubernetes. This keeps the diagram readable without making people maintain data that the cluster already knows.

## Keep the boundary explicit

| Author in LikeC4 | Generate from Kubernetes |
| --- | --- |
| systems, containers and relationships | instances of mapped workload controllers |
| environments, cluster targets and important namespaces | namespaces with mapped workloads that are not authored |
| deployment views and their scope | images, image IDs, versions, Helm charts and replica status |

Non-terminal Pods are short-lived evidence for observed `imageID` values. ReplicaSets connect Pods to Deployments, and Jobs connect Pods to CronJobs. They do not become deployment nodes. The diagram shows the controller deployment unit and normalized replica counts instead.

The optional [`@architecture-model/kubernetes`](https://www.npmjs.com/package/@architecture-model/kubernetes) package generates this observed part as a committed LikeC4 overlay. A repository made from the template does not depend on it unless you install it.

## Declare every cluster

Declare a `namespace` deployment kind and put explicit synchronization metadata on each cluster. Use exact kubeconfig context names and an explicit namespace list while introducing the model.

```
specification {
  deploymentNode environment
  deploymentNode cluster { technology 'Kubernetes' }
  deploymentNode namespace
}

deployment {
  environment production {
    cluster eu {
      metadata {
        kubernetesContext 'production-eu'
        kubernetesNamespaces ['shop', 'workers']
        kubernetesElementAnnotation 'architecture.example.com/likec4-element'
        kubernetesIgnoreAnnotation 'architecture.example.com/likec4-ignore'
      }

      namespace shop {
        metadata { kubernetesNamespace 'shop' }
      }
    }
  }
}

views {
  deployment view production {
    title 'Shop: production deployment'
    include production.**
  }
}
```

Repeat the cluster target for every context. `kubernetesExcludeNamespaces` removes namespaces from a list or from `kubernetesNamespaces '*'`. An authored namespace joins the Kubernetes namespace through `kubernetesNamespace`; namespaces with mapped workloads and no authored match are generated. Views remain authored because their scope expresses what a reader needs to see. Select generated content through stable authored ancestors such as `include production.**`; do not reference generated FQNs directly.

Use an annotation name under a domain your organization controls. Put it on the workload controller and map it to an existing, fully qualified LikeC4 element:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "shop-api.fullname" . }}
  annotations:
    architecture.example.com/likec4-element: shop.api
  labels:
    app.kubernetes.io/version: {{ .Chart.AppVersion | quote }}
    helm.sh/chart: {{ printf "%s-%s" .Chart.Name (.Chart.Version | replace "+" "_") | quote }}
spec:
  template:
    spec:
      containers:
        - name: api
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

The mapping belongs on the Deployment, StatefulSet, DaemonSet or CronJob itself, not only under `spec.template.metadata`. It points to an independently deployable software system, container or custom kind, never a person or component.

An incidental controller in a mixed namespace can instead carry the configured ignore annotation with a reason:

```yaml
metadata:
  annotations:
    architecture.example.com/likec4-ignore: 'Platform-managed helper, not architecture-significant'
```

Do not put both mapping and ignore annotations on one controller.

## Refresh the snapshot

Install the package in the architecture repository:

```bash
npm install --save-dev @architecture-model/kubernetes
```

Pass one LikeC4 project directory as the workspace. If the repository contains several LikeC4 projects, run the command against the project that owns these Kubernetes targets, not their common parent.

The kubeconfig identity needs list access to namespaces, the four supported controller kinds, Pods, ReplicaSets and Jobs in scope. Run the read-only check first:

```bash
npx architecture-model-kubernetes discover model
```

Discovery prints mapped controllers with their LikeC4 FQNs, intentionally ignored controllers with their reasons, and unmapped controllers. Resolve each unmapped controller by adding a mapping or ignore annotation, or deliberately taking its namespace out of the authored scope. Discovery does not write a file and does not fail merely because an unmapped workload exists.

Discovery reports successful contexts and every access failure before it exits nonzero. Unknown or non-deployable mappings and explicitly configured namespaces that are absent from the cluster are errors. A model with no synchronization targets is an error rather than an empty snapshot.

Each context has a 30-second discovery deadline. Pass `--timeout-seconds number` to both commands for a larger cluster or slower API path. Within one context, the command reads at most four namespaces concurrently, including when the target selects `'*'`. The deadline aborts Kubernetes HTTP requests, but it cannot interrupt a kubeconfig exec credential plugin that blocks while asking for authentication. Refresh interactive credentials first.

Then generate and review the complete snapshot:

```bash
npx architecture-model-kubernetes sync model
npm run validate
npm run build
git diff -- model/deployment.generated.c4
```

When the generated file has a custom path, pass the same `--output path/inside/model.c4` to both `discover` and `sync` so discovery excludes the previous generated snapshot.

If any context is inaccessible or the generated LikeC4 is invalid, synchronization preserves the previous file. It also refuses to replace an existing file unless that file carries its generator ownership marker. Do not remove a failed target to create a partial snapshot. Fix access, metadata or model errors and rerun the complete sequence.

`model/deployment.generated.c4` is generated data: do not edit it. Review changed images, image IDs, versions and replica counts, then commit the snapshot manually when it is acceptable. The generated title names the Kubernetes controller; `instanceOf` retains its logical association. Logical relationships stay authored and LikeC4 resolves inherited edges through the deployment hierarchy rather than connecting every instance to every other instance.

Refresh after releases or before architecture reviews. Use repository history to establish snapshot age because the generated overlay has no timestamp. Registry names, versions and image IDs may be sensitive when the repository or site is public. Use dynamic views for important flows and quality scenarios for availability, failover and capacity expectations; a deployment snapshot is not the whole architecture.
