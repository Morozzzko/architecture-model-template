Documentation goes out of date, and the names of people go out of date first: teams reorganize, people change roles and leave. A field like "Owner: Payments team" stays correct for longer only because it says so little. When a payment provider's webhooks fail at night, it doesn't say whom to call.

So instead of one owner, each system records whom to go to for each kind of task. Different tasks often need different people:

| Field | Who | Ask them when |
| --- | --- | --- |
| `integratedBy` | integrated it originally | you need to know why it works the way it does |
| `experts` | know best how it works and how its integration is changed | there is an incident, an API or contract change, an upgrade, or a change to review |
| `contributors` | have worked on it | you need reviewers or extra hands, or the experts are away |
| `administrators` | manage it: for a vendor, the account, keys, billing and support; for our own, its accounts and access | credentials need rotating, someone needs access, or a support ticket or plan change is due |

The person who manages a vendor account is often not the one who knows how to change the integration, and neither of them may have built it. A question sent to "the owner" usually gets passed on until it reaches one of these people; the fields name them directly. The `owner` field stays, for the team that is accountable for the system.

## External systems too

What we know about an external system is known by our own people: who connected it, who can debug it, who has the login to the vendor's account. The vendor's documentation doesn't contain any of that, and it is easily lost when those people move on. So external systems have the same fields as our own.

## Keeping the fields useful

- **Contributors are a longer list than experts.** When the experts have moved on, someone among the contributors can usually say whom to ask next. When you need people to work on an integration, start from this list.
- **A date says how old the fields are.** `peopleConfirmed` is when someone last checked them. When it is more than about six months old, the coding agent asks you to check them again the next time you work on the system with it.
- **Each person is listed once.** The fields hold handles from `model/people.json`, so renaming someone is one edit. When someone leaves, they are marked as having left in that file and stay in the fields, which lets you [find systems whose people have left](../recipes/people-who-left/).
- **What the model already says isn't written down again.** Which systems and containers use a system is worked out from the model's relationships, so it is correct as long as the relationships are.
- **The agent proposes contributors from git, and you confirm them.** The authors of the code that integrates a system are a good first guess, but having changed a file doesn't mean someone understands the system, so the agent records only the people you confirm.
