ISO/IEC/IEEE 42010 separates a system's architecture, its fundamental concepts and properties and the principles behind them, from the architecture description that expresses it. This repository is the description. A good one says both why the system exists and what parts it has, and stays true as the system changes.

One repository describes all of an organization's systems: the model holds every one of them, and each has its own page that says why it exists and what it's made of. The steps below are for one system; repeat them for the next.

A coding agent writes most of it. It can read code, compose files and infrastructure manifests to find the parts. Only you know why they are there. This page is the order to work in, as prompts for the agent; the diagrams come from an example shop modeled the same way.

## Before you start

Make a repository as described in [Start a repository](../../start/), and install the Claude Code plugin in it:

```
/plugin marketplace add Morozzzko/architecture-model-template
/plugin install architecture-model@architecture-model
```

The agent learns the repository from `AGENTS.md` and the modeling rules from the plugin's `c4-modeling` skill. Have at hand what it can read for itself: repositories, `docker-compose.yml`, Terraform or Kubernetes manifests, runbooks.

## What ages and what doesn't

Documentation goes stale where it copies something that changes. Each kind of content has one home:

| Content | Changes | Lives in |
| --- | --- | --- |
| Purpose, stakeholders, quality goals, key concepts | Rarely | Prose on the system's page in `src/content/docs/systems/` |
| Principles and the reasons for decisions | Rarely, and then by a new decision | ADRs, summarized on the system's page; an ADR is superseded, never rewritten |
| Systems, containers, relationships | With the code | The model; pages pull it in through components, and the build fails when a page names something the model lacks |
| Providers, regions, owners, lifecycle | Often | Deployment and metadata in the model, refreshed by the agent from their sources |
| Anything computable from the model | Never by hand | A derived value, computed at build time |

Never restate the model in prose. "The Orders API writes to the orders database" in a paragraph goes stale; the same sentence as a relationship stays checked.

## Why the system exists

Start here, before any box. It's the part an agent can't read from code, and the part readers need first.

### 1. Purpose and stakeholders

> Interview me about the Shop: what it is for, and who depends on it and what each of them cares about. Write the answers under Purpose on the Shop's system page.

### 2. Quality goals

Every system trades qualities against each other: a payment system gives up speed for correctness, a prototype gives up maintainability for speed of delivery. The quality goals say which trade-offs this system makes, and they explain more of its structure than any diagram. Ranking the top few goals and backing each with a scenario comes from [arc42](https://arc42.org/), by Gernot Starke and Peter Hruschka, [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/).

The interview follows the ISO/IEC 25010 quality model without asking you to learn it. Pick the three kinds of quality that matter most, then the specific qualities within them, then a scenario someone could check, and who needs it:

| Kind of quality | The question it answers |
| --- | --- |
| Functional suitability | Does it do the right thing, completely and correctly? |
| Performance efficiency | Is it fast enough, and does it use resources sensibly? |
| Compatibility | Does it work alongside and exchange data with other systems? |
| Interaction capability | Can its users learn and use it, including users with disabilities? |
| Reliability | Does it keep working, and recover when something fails? |
| Security | Does it protect data and actions from people who shouldn't have them? |
| Maintainability | Can the team understand, change and test it safely? |
| Flexibility | Can it move to other environments, scale or adapt? |
| Safety | Can it avoid harming people, property or the environment? |

> Interview me about the Shop's quality goals: help me pick the top three kinds of quality, then the specific qualities, then a checkable scenario and who needs each one. Write them into Quality goals and Quality scenarios on its page.

A goal is useful when someone could check it: "a placed order is confirmed to the customer within two seconds at peak load, because customers abandon slow checkouts", not "fast".

### 3. Key concepts

> Ask me for the handful of concepts the Shop is built around, and put them under Key concepts on its page.

For example, in the shop: an order is a sequence of events, and a payment counts only once the chain confirms it. Concepts like these explain the boxes that follow, and they rarely change.

## How the why and the what meet

### 7. Principles and decisions

Every structural choice in the model has a reason, and the reason is what outlives the choice.

> Go through the containers view and ask me why each significant choice was made. Record each answer as an ADR with bin/adr, and summarize the principles under Principles and decisions on the Shop's page.

For the example: "Order events go through Kafka so Billing never calls the Orders API" is a principle; the `order-placed` topic is how it shows in the model.

### 8. Conventions

Some questions have more than one reasonable C4 answer, and the agent would answer them differently from one session to the next. Settle each once in `model/conventions.md`, which the agent reads first:

| Kind of question | Example convention |
| --- | --- |
| Where the line is | Caches are containers of the system that owns them. |
| How much detail | Topics are containers only when another team consumes them. |
| Cross-cutting services | Observability is drawn once, at system level. |
| Other teams' systems | Another team's system is one external box. |
| Providers | Payment providers are separate systems, because we route by country. |
| Environments | Only production and development are modeled. |
| Naming | Titles are product names; repository names go in links. |
| People | Actors are roles with different access, not job titles. |

> Record in model/conventions.md that observability is drawn once, at system level.

### 9. Where it's heading

A description that only shows the present can't explain the past or warn about the future.

> Mark the Payments v1 integration as being replaced, and add the planned Payments v2 with a note on why, linking the ADR.

With the [editable-metadata](../../addons/editable-metadata/) addon, a lifecycle field shows this in tables and can be changed in the dev server.

## Keeping it true

Run this whenever the system changes noticeably, and before you rely on the description:

> Compare the model with the repositories and infrastructure. List what is missing, gone or different, and fix the model. Don't change the why sections; ask me if something there looks wrong.

An agent that writes from code tends to write about the code: ports, libraries, class names, "highly scalable". Before merging what it wrote, have critics read it:

> Review the Shop's page and model with the architecture-review skill.

The plugin's `architecture-review` skill runs five critics, each seeing only the documentation: a newcomer who must answer questions from it, a noise auditor, a rationale skeptic, a C4 inspector and a quality examiner. It deletes and rewords what they flag, and brings everything new back to you as questions instead of inventing it.

Then review what the build can't check:

- The why sections still describe the system's purpose and goals.
- Every element has a description, and every container a technology.
- No relationship is labeled "Uses".
- Every view title says what it shows.
- Decisions made since the last review have ADRs.
- `npm run validate` and `npm run build` pass.
